## Faits mesurés (jobs jetables a0-spike2 / a0-spike3, 2026-09-02, supprimés)

6. **Un XML qui porte déjà une `ParametersDefinitionProperty` + `properties([parameters])` ⇒ DEUX propriétés** (7 noms relus, dont doublons) et le job **casse** (`buildWithParameters` ⇒ HTTP 500, le webhook enfile un build qui ne démarre pas). Le step ne retire jamais une propriété qu'il n'a pas posée — même de sa propre classe. Avec un XML **sans** paramètre : une seule propriété ; `options{disableConcurrentBuilds}` et `triggers{GenericTrigger}` **déclaratifs** sont préservés à l'amorçage (`POST /build` 201), au `buildWithParameters` et au build par webhook (`triggered:true`, la variable GWT s'ajoute aux paramètres liés). Corollaire de rollout : **la conversion d'un job à formulaire passe par une RE-POSE** (POST config.xml efface paramètres ET trackers) puis un amorçage ; un simple `git push` du Jenkinsfile sur un job dont le XML garde ses paramètres le casse.
7. **`EnvVars.resolve()` frappe aussi les paramètres `password`** : `A$$B${JENKINS_HOME}C` arrive au shell en 21 octets (`A$B/var/jenkins_homeC`) par le canal natif, en 20 octets intacts par `withEnv(["P=${params.P}"])` (sha256 égal à l'attendu). Un mot de passe annuaire contenant `$$` ou `${` est donc altéré aujourd'hui avant Vault (lockout AD au deuxième essai).
8. `params.X` d'un paramètre `password` est un **`hudson.util.Secret`** dans le sandbox (sa `toString()` rend le clair — d'où `"${params.X}"` = valeur brute ; `.length()` n'existe pas) ; `env.X` en Groovy est la valeur **résolue** (fait 7) ; une valeur vide en `withEnv` retire la variable (`EnvVars.override`), ce que `${VAULT_USER_PASSWORD:-}` côté lib absorbe (PLAN-only inchangé).
9. **Un secret interpolé dans un argument de step est PERSISTÉ EN CLAIR** (jobs jetables a0-spike4/5, revue adverse du commit `a639199`) : `withEnv(["P=${params.P}"])` avec `P=A$$B${JENKINS_HOME}C` ⇒ la valeur BRUTE est écrite dans `builds/<n>/workflow-completed/flowNodeStore.xml` (le masquage des arguments de step est par ÉGALITÉ avec la valeur d'environnement, donc résolue — inapplicable précisément aux mots de passe que le fait 7 vise), et Jenkins l'écrit lui-même dans la console : « A secret was passed to "withEnv" using Groovy String interpolation, which is insecure ». Un mot de passe sans `$` n'apparaît nulle part (masqué). Comparer `"${params.P}"` à `env.P` dans un `script{}` (aucun step) ne persiste rien et détecte l'altération (`equal=false` pour `A$$B…`, `equal=true` pour un mot de passe plat).
10. **Un job RE-POSÉ perd ses `options{}`/`triggers{}` déclaratifs au premier build** dès qu'un `properties()` scripté s'y ajoute (jobs jetables a0-spike6, puis `selfservice-app-deploy` #34 et #36) : sur un job NEUF la combinaison survit (fait 6), mais après un `POST config.xml` sur un job déjà amorcé, le premier build laisse le job **sans trigger ni option** (webhook 404) jusqu'au build suivant. Tout dans `properties([disableConcurrentBuilds(), pipelineTriggers([…]), parameters([…])])` avec un XML qui porte déjà trigger et option ⇒ **doublon** sur un job neuf. La seule combinaison stable dans les deux chemins : **les trois propriétés posées par `properties()`, et un XML SANS AUCUNE propriété** — un trigger, une option, une propriété de paramètres après l'amorçage, job neuf comme job re-posé, webhook vivant.

## Décisions

### D1 — `provision-plan` : la forge relue AVANT le verdict, le statut nourri par les faits

- **`scripts/lib/gitea-pr-confirm.sh`** (à sourcer) : `gitea_pr_confirm <n> <head_ref_attendu> [base_attendue]` — `GET /repos/<repo>/pulls/<n>` (python, token par env, `timeout=30`) ; rc 0 et lignes `GITEA_STATE=open`, `GITEA_HEAD_REF`, `GITEA_HEAD_SHA`, `GITEA_BASE_REF` sur stdout **seulement si** `state == open`, `head.ref == attendu`, `head.ref` ~ `^provision/`, `base.ref == base attendue` ; sinon rc 1 et `FORGE_NON_CONFIRMEE : <raison>` sur stderr (404, 5xx, timeout, non-objet, champs absents, `\n` dans une valeur, mismatch, fermée/mergée). Le numéro est validé `^[0-9]+$` avant de composer l'URL.
- **`scripts/provision-plan.sh`** : après la garde `provision/*`, **avant** le clone : `gitea_pr_confirm "$PR_NUMBER" "$PR_BRANCH" "$GIT_BASE"` ⇒ refus rc 1 sans commentaire ; le clone checkoute **`GITEA_HEAD_SHA`** relu par `git checkout --detach` (lie le numéro au contenu : une branche `provision/<app>-<env>` réutilisée après merge ne fait pas commenter une PR mergée ; `--detach` parce que `checkout -- <sha>` prendrait le SHA pour un chemin — mesuré), `|| REFUS: BRANCHE_INTROUVABLE` rc 1 ; le bloc de plan est un **sous-shell** (revue, bloquant : dans un groupe `{ }`, `exit 1` tuait le script sans verdict ni faits — une PR qui SUPPRIME un manifeste rend désormais un ❌ commenté) ; fichier de faits `PLAN_FACTS` (si posé) : faits INITIAUX `refus SCRIPT_INTERROMPU` dès le prologue (une mort inattendue laisse un fichier honnête, jamais celui du build précédent — le Jenkinsfile le retire aussi avant l'appel), puis réécrits sur **chaque** sortie : `PLAN_PR_NUMBER`, `GITEA_HEAD_REF`, `GITEA_HEAD_SHA`, `PLAN_VERDICT=refus|ignore|ok|fail`, `PLAN_REASON` ; le verdict posté cite la tête relue et lie `src/commit/<sha>/<manifeste>` (jamais la tête mouvante de la branche) ; un commentaire de verdict impossible ⇒ `refus COMMENTAIRE_ECHEC`. Changement de parité assumé et écrit : un `checkout` raté ne rend plus vert. L'appel enchaîné de `provision-request.sh` [5/5] (PR ouverte, branche = head) reste vert.
- **`scripts/provision-plan-status.sh`** : lit `PLAN_FACTS` (fichier, sinon les mêmes faits chargés en environnement par le post de stage) ; des faits qui nomment une **autre** PR (`PLAN_PR_NUMBER`) sont périmés ⇒ silence ; **faits absents** (le stage n'a pas tourné) ⇒ relecture de la forge par la **même** lib ; non confirmé ⇒ `exit 0` sans commentaire. Corps (sans accents), le **verdict d'abord** (revue : un ABORTED/UNSTABLE après un verdict rendu ne dit plus « aucun verdict ») : `ok`+`SUCCESS` ⇒ upsert **seulement si** un statut existe déjà (`COMMENT_ONLY_IF_EXISTS=1`) ; `ok`+autre ⇒ « verdict RENDU, build termine <resultat> apres coup » ; `fail` ⇒ « verdict NEGATIF, voir provision-plan » ; `ignore` ⇒ « demande IGNOREE (<raison>) : aucun verdict » ; `refus` ⇒ « REFUS avant le verdict : <raison> » (dont `COMMENTAIRE_ECHEC`) ; sans faits : `ABORTED` ⇒ « abandonne, aucun verdict, rejouer le webhook », `SUCCESS` ⇒ upsert seulement si existant, sinon « ECHOUE (<resultat>) avant le plan, voir le log » ; repli `BUILD_REF` = `JOB_NAME #BUILD_NUMBER` quand `BUILD_URL` est vide. Marqueur `<!-- provision-plan-build -->`.
- **`scripts/lib/gitea-pr-comment.sh`** : `urlopen(timeout=30)` ; pagination `?limit=50&page=N` **jusqu'à page vide** (ou page répétée par ses ids) — jamais « page plus courte que 50 » : Gitea plafonne `limit` à `api.MAX_RESPONSE_ITEMS` (revue : avec un plafond de 30, le marqueur en 55e s'empilait) ; knob `COMMENT_ONLY_IF_EXISTS=1` (marqueur absent ⇒ `COMMENT_SKIPPED`, rc 0). **`scripts/lib/gitea-pr-confirm.sh`** refuse aussi un `head.sha` non hexadécimal (jamais un argument libre pour git) et une PR depuis un **fork** (sa tête n'est pas dans le clone).
- **`ci/Jenkinsfile.provision-plan`** : `sh 'set +x; PLAN_FACTS="$WORKSPACE/.plan.facts" bash scripts/provision-plan.sh'` ; `post{always}` de **stage** qui charge les faits dans `env.` (`GITEA_HEAD_REF`, `PLAN_VERDICT`, `PLAN_REASON`) ; `post{always}` de **pipeline** : `script { if (!(PR_BRANCH ~ provision/*) || !(PR_NUMBER ~ [0-9]+)) { echo; return } ; try { timeout(2 min) { node { checkout scm ; withCredentials ; withEnv([BUILD_RESULT]) { dir { sh 'set +x; bash scripts/provision-plan-status.sh || echo AVERTISSEMENT' } } } } } catch (e) { echo AVERTISSEMENT } }`.
- **`ci/Jenkinsfile.provision-apply`** : même garde Groovy avant le `node` du `post{always}`, `try/catch` + `timeout` (le gate forge `GITEA_HEAD_REF` du `sh` reste).
- **`provisioning-request`** : pas de `post{always}` — documenté avec ses nuances (la PR naît en [4/5] ; [5/5] non fatal ; au rejeu une PR peut préexister et un échec avant [4/5] la laisse muette ; `ERR`/réponse illisible après `POST /pulls`) ; épreuve statique de ces faits.

### D2 — `selfservice-app-deploy` : formulaire posé par le Jenkinsfile, XML sans paramètre

- **`ci/Jenkinsfile.selfservice`** : le bloc `parameters{}` disparaît ; premier stage « Formulaire — paliers dérivés de la chaîne » sous `dir('poc-control-plane-federation')` : `bash -c '. scripts/lib/env-chain.sh && env_chain_nonprod' > "$WORKSPACE/.a0-envs"`, `readFile`, chaque palier validé `^[a-z0-9]+$` (`FORMULAIRE_INVALIDE`, définitions précédentes conservées), puis `properties([parameters([ … 8 … choice(name: 'ENVIRONMENT', choices: envs) … ])])` — descriptions verbatim  ; **pas d'`options{}` ni de `triggers{}` déclaratifs** : `disableConcurrentBuilds()` et `pipelineTriggers([GenericTrigger(stoa-selfservice-plan …)])` sont dans le même `properties([…])` (fait 10 — amendement après revue live : sur le job re-posé, le premier build perdait trigger et option). Les trois stages suivants (Référence, Plan, Apply) passent sous `withEnv(["MANIFEST=${params.MANIFEST ?: (env.MANIFEST ?: '')}", "MERGE_SHA=…", "ENVIRONMENT=…"])` (Référence, Plan) et `[… "ADMIN_VIA=…", "DEBUG=${params.DEBUG ?: false}", "VAULT_USER=…", "USER_VAULT_JWT=…"]` (Apply) — fait 7 pour les sept paramètres NON secrets ; le repli `env.MANIFEST` sert le PLAN par webhook tant que le paramètre n'est pas matérialisé (fenêtre re-pose → amorçage). **Le mot de passe ne traverse AUCUN step** (fait 9, amendement après revue) : il reste sur le canal natif, et l'Apply ouvre par une garde `script{}` — `"${params.VAULT_USER_PASSWORD}"` (brut) ≠ `env.VAULT_USER_PASSWORD` (résolu) ⇒ `error('REFUS: MOT_DE_PASSE_ALTERE …')` AVANT tout appel à Vault (aucun lockout), avec pour issue la voie B (JWT) ou un mot de passe sans `$`. Ordre Formulaire < Référence < Plan < Apply, ancré.
- **`scripts/setup-selfservice-job.sh`** : knob `XML_PARAMS` (`auto` : `no` quand `SCRIPT_PATH` est `Jenkinsfile.selfservice` — le XML ne porte alors **aucune** propriété, ni paramètre ni trigger ni option, le Jenkinsfile pose tout, faits 6 et 10 —, `yes` sinon : `publish-api-deploy` garde son bloc déclaratif, ses paramètres XML comme ceinture SECURITY-170, son trigger et son option dans le XML) ; en mode `yes`, la `<choices>` d'`ENVIRONMENT` est **dérivée à la pose** de `env_chain_nonprod` (validée, échappée par ElementTree — plus de littéral) ; `--print` (XML rendu sur stdout, zéro réseau) ; amorçage `POST /build` (sans paramètre XML) ou `buildWithParameters` ; `BOOTSTRAP_WAIT` (défaut 360 s) avec « encore en cours » distingué d'un échec ; **relecture après amorçage** : exactement UNE `ParametersDefinitionProperty` (fait 6, sinon message « job cassé par un push sans re-pose : re-poser ») et, en mode `no`, `ENVIRONMENT == env_chain_nonprod`, UN trigger `stoa-selfservice-plan` et UNE option posés par le build (fait 10). Résiduel nommé : ce poseur n'a ni auth Jenkins ni portail (parité avec `setup-provision-jobs.sh` à faire le jour du rollout client).
- Hors périmètre, nommé : `ci/Jenkinsfile.publish-api:24` (liste du producteur avec terminus), `ci/Jenkinsfile.api-promote-request:44`.
