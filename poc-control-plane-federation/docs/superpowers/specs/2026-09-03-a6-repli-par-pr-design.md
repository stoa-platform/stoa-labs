# A6 — Le repli : re-convergence à l'état N-1, sans changer de clé

## Porte (reprise du GOAL, non négociable)

- **Porte A6 :** deux applies successifs de la même application ⇒ **même GUID d'application, même clé** ; rollback rec ⇒ état de la gateway = état au SHA N-1 (identifiers, IP, cert), **vérifié par lecture, pas par log**.
- **Contre-épreuve :** rollback vers un SHA dont l'API n'est plus au palier ⇒ `API_NOT_PROMOTED` (A5 tient aussi en repli) ; rollback au terminus sans référence ITSM ⇒ refus (le motif G6).
- **Deux règles mesurées (spike S1, 2026-09-02), non négociables :** (1) la chaîne **ne désinscrit jamais** (`DELETE …/apis` sur une paire qui a servi est irréversible en 10.15) — un repli re-converge identifiers et policy, jamais la souscription ; (2) le **retrait** d'une application est une **suspension** (`isSuspended`), pas une désinscription.

## La thèse, en une phrase

Le GOAL dit « on promeut la **demande**, pas l'objet ». Alors **on replie la demande** : le repli d'une application au palier est une **PR de repli** `provision/<app>-<env>` dont la ligne `per_env.<env>` et le certificat `certs/<app>-<env>.crt` redeviennent, **à l'octet**, ceux du SHA de merge **précédent** (N-1) de cette même branche. Puis la chaîne existante — merge (ADR-081) → `provision-apply` (portes A4 deux fois, pause nominative) → `selfservice-app-deploy` (garde A3, rôle avec porte A5, verify) — l'applique **comme tout apply**. Rien de nouveau en aval ; le verbe est la convergence idempotente (spike S1 : 4822/0, GUID et clé stables), donc l'application garde son GUID et sa clé.

C'est le port exact d'**ADR-085** : G6 ne re-appliquait pas un vieux commit, il écrivait le contenu N-1 de `deploy.<env>.yaml` **verbatim dans un commit NEUF sur main**, puis re-appliquait ce commit. Pour les applications, « le fichier de déploiement du palier » est la PR (GOAL :116, décision de forme) — le commit neuf est donc une PR.

## Hypothèses (session autonome — ce qu'un humain aurait tranché)

1. **Le repli est une PR, pas un re-dispatch direct du SHA N-1** (le « levier » annoncé par `ci/Jenkinsfile.selfservice:194` et `ENVIRONNEMENTS.md:1038` : un `MERGE_SHA` saisi à la main sur l'aval). Cinq raisons, dans l'ordre de poids : (a) **`PALIER_SUPPLANTE`** (A2, `provision-apply-reconcile.sh:269-276`) refuse structurellement de re-projeter un état dépassé — rejouer le webhook de N-1 est refusé, et c'est juste : le repli n'est pas une exception à cette règle, c'est un état **nouveau** sur `main` dont le contenu est celui de N-1 ; (b) **la lignée du rôle** : un re-apply du SHA N-1 checkoute l'arbre entier d'alors (rôle, lib, gardes d'alors — la limite écrite en A5-D7 et ADR-088 :65) ; la PR de repli est appliquée à **son** SHA de merge, arbre d'aujourd'hui — la limite A5-D7 **se dissout** au lieu d'exiger un « plancher de SHA » ; (c) **Git redevient la vérité** après le repli (le dernier merge de `provision/<app>-<env>` dit ce que la gateway sert), et le rejeu d'un webhook ancien ne défait pas le repli en silence ; (d) **toutes les portes s'appliquent sans une ligne de code** — quatre yeux, `deployerGroup`, refs, ITSM, terminus par position, A5 ; (e) le motif G6 (commit neuf, contenu N-1). Coût assumé : un merge humain de plus qu'un job direct — en `rec` (`selfApproval`) le demandeur merge lui-même, en `int`+ c'est le quatre-yeux que DORA art. 17(1)(b) exige de **tout** changement, repli compris (G6 a gardé le `change_ref` au rollback pour la même raison). Le levier direct n'est **pas retiré** par A6 (c'est la propriété A2 « un SHA de la lignée est accepté ») mais **renommé** : ce n'est pas le repli, c'est un rejeu hors chaîne borné par A3 — les deux commentaires sont réécrits (D8).
2. **N et N-1 sont définis par la LIGNÉE de la branche**, sur la première parenté de `main` : les commits de merge dont le sujet Gitea porte `(#n) from provision/<app>-<env> into main`, **chacun confirmé par la forge** (PR n : `merged`, `head.ref` == la branche, `merge_commit_sha` == le commit — motif A0 `gitea-pr-confirm` / A2 « Gitea = la vérité sur la PR, Git = la vérité sur main »). N = le dernier, N-1 = le précédent. Sans N ⇒ `AUCUNE_LIGNEE` ; sans N-1 ⇒ `AUCUN_ETAT_PRECEDENT` (le `NO_PREVIOUS_STATE` 409 de G6) — remède nommé : le retrait est une suspension, pas un repli. Limite : la clé est le sujet du **merge commit** de Gitea (le style « squash » ou « rebase » la perd) — le lab merge ainsi ; un client qui squashe déplace la clé vers le trailer `Provision-Branch` que le commit de branche porterait (hors A6, écrit).
3. **Le repli restaure l'état DÉCLARÉ N-1 (Git), pas l'état SERVI.** Aucune trace machine « appliqué » n'existe dans Git pour les applications (GOAL :116 ; le SHA appliqué ne vit que dans le commentaire de PR et les `buildVariables`) — A6 n'invente pas de registre. Un N-1 mergé puis **refusé à l'apply** (ex. A4 live : #435 `FOUR_EYES_VIOLATION`, jamais projeté) est restauré tel que déclaré et **repasse toutes les portes** ; la PR de repli cite la lignée et le digest attendu pour que le mergeur voie ce qu'il restaure. Garde de cohérence : `digest(main, env) == digest(N, env)` sinon **`REFERENCE_DIVERGENTE`** (quelqu'un a écrit `main` hors PR — le repli ne raisonne pas sur un état qu'aucune PR ne porte).
4. **L'application et le palier SONT saisis** (formulaire) — contrairement à G6-D1 — parce que la paire (app, env) **est** l'identité du fichier de déploiement (la branche) ; il n'y a pas d'autre poignée (pas d'objet « promotion »). Tout le reste — N, N-1, digest, ligne, cert — est **dérivé, jamais saisi**. La liste des paliers du formulaire est la **chaîne entière**, terminus compris : le repli est d'abord un geste de terminus, et c'est la seule voie d'application qui le nomme — les portes décident (`GATE_REFS_REQUIRED` à la demande, puis A4 : `REQUESTER_UNKNOWN`, ITSM, `TERMINUS_SANS_VOIE` jusqu'à A7).
5. **`change_ref` : exigé à la DEMANDE de repli si la porte du palier l'exige** (`env_chain_gate` ⇒ `GATE=1|…`, c'est-à-dire `requireChangeRef || itsmCheck` — le prédicat de G6-D3 et de `provision-apply-gate.sh:181`) ⇒ `GATE_REFS_REQUIRED` **au plus tôt**, avant tout clone et tout appel de forge, aucune PR ouverte. Fourni, il **remplace ou ajoute** `change_ref` dans la ligne restaurée (G6-D4 : un vrai ITSM a passé le change de N-1 à « implemented », un repli d'urgence porte **son** change). **`pv_ref` n'est jamais exigé ni touché** (G6-D3 : le PV atteste la recette de l'état qu'on quitte ; l'état restauré a porté le sien). Sans `CHANGE_REF` fourni et sans exigence : ligne **verbatim**.
6. **La racine du manifeste ne bouge pas.** A1 la fige (`CONTRAT_DIVERGENT`) ; si elle diffère entre N-1 et N (édition hors flux), refus **`RACINE_DIVERGENTE`** — la restaurer toucherait les autres paliers. Le repli ne raisonne que sur la ligne `per_env.<env>` et le cert du palier. La contre-vérification est gratuite : `app_manifest_digest_env` (racine ⊕ `per_env.<env>`) sur l'arbre de la PR de repli **doit** égaler `digest(N-1, env)` — sinon `RESTAURATION_INFIDELE`, rien n'est poussé.
7. **Périmètre de la PR de repli = son manifeste + son certificat** (A2 `PR_HORS_PERIMETRE` le tient déjà). Le cert `clients/provisioned/certs/<app>-<env>.crt` est restauré **à l'octet** : présent à N-1 ⇒ `git show N-1:…`, absent à N-1 et présent à N ⇒ supprimé, absent des deux ⇒ rien.
8. **Identité : la PR de repli est ouverte par le token `ci`** (comme `provision-request.sh`, la voie livrée) ; le demandeur du repli (`jenkins-form:<uid>`, le motif d'`app-request`) est dans le commit (trailer `Repli-Par`) et le corps de la PR. Sur `int`+ la porte A4 refuse `REQUESTER_UNKNOWN` tant qu'A7 n'ouvre pas les PR sous identité humaine — le repli **hérite** la limite et la lève avec A7 sans changement (même script d'ouverture de PR à faire évoluer).
9. **« Même GUID, même clé » est une propriété de la convergence, vérifiée par LECTURE** : verify relit `SUBSCRIPTION_CONFIRMED (id=<GUID>)` (A5-D3) et `CERT_NAME_CONFIRMED` ; le harnais live lit `GET /applications/{id}` avant/après (GUID, empreinte sha256 des identifiers et de la clé d'accès, plage IP, cert) **sans jamais imprimer la clé**. Le rôle n'apprend rien : A6 ne touche ni `main.yml` ni `verify.yml`. Rien n'est désinscrit (règle 1) ; A6 n'écrit pas la suspension (règle 2 — verbe de retrait, `isSuspended` n'existe nulle part dans le rôle ; nommé en D9).
10. **Le repli du repli est un repli** : la lignée est linéaire, la PR de repli N+1 est un merge de `provision/<app>-<env>` comme les autres, donc « replier N+1 » restaure N. Pas de 409 « double rollback » comme G6 (qui recyclait un marqueur) — écrit tel quel.

## État courant (relevé du 2026-09-03, à ne pas re-dériver)

- **La référence d'un palier** (A2) : `provision-apply-reconcile.sh` dérive `<app>`/`<env>` de `PR_BRANCH` (dernier tiret), relit la forge (mergeur, demandeur, fichiers touchés — `PR_HORS_PERIMETRE` hors manifeste+cert), puis compare `app_manifest_digest_env(SHA mergé, env)` à `app_manifest_digest_env(origin/main, env)` : différent ⇒ `PALIER_SUPPLANTE` (« rejouer une demande, ou le repli (A6) »). L'aval checkoute l'arbre **entier** au `MERGE_SHA` (rôle, lib, manifeste), la garde A3 seule est extraite d'`origin/main`.
- **Le manifeste** (A1) : `clients/provisioned/applications/<app>.ansible.yml`, racine figée + bloc `per_env:` dont chaque palier tient sur **une ligne flow** `    <env>: { … }` ; `app_manifest_merge_env <fichier> <env> '<mapping>'` remplace ou insère **cette seule ligne**, textuellement, avec auto-vérification (rechargement `BaseLoader`, égalité du mapping) ; `app_manifest_digest_env` donne `sha256:` du manifeste effectif du palier. Le cert par palier : `clients/provisioned/certs/<app>-<env>.crt` (`provision-request.sh:409`). `provision-request.sh` n'écrit **jamais** `change_ref`/`pv_ref` (le harnais A4 les a fusionnés par la lib ; « A7 porte le champ ») — `provision-apply-gate.sh:160-183` les lit dans `per_env.<env>` du manifeste mergé.
- **La demande** (`provision-request.sh`) : branche `provision/<app>-<env>` recréée depuis `main`, commit `provision(<env>): application <app> (demande <caller>)`, push forcé (branche machine), `POST /pulls` idempotent (EXIST sur `head.ref`), plan enchaîné (`provision-plan.sh`). Liste des paliers = `env_chain_nonprod` (`ENV_INVALIDE` au-delà — le terminus est exclu par structure pour une demande).
- **La lignée sur le lab** (gitea main, 2026-09-03) : les merges Gitea s'écrivent `Merge pull request 'provision(<env>|<user>): <app>[-<env>] [CHG-…]' (#n) from provision/<app>-<env> into main` ; une même branche est mergée plusieurs fois (`provision/a4p1788394281-int` : #433, #435, #437, #439 — trois refusées à l'apply, une projetée) ; `provision/a4p1788394281-prod` : #442 (draft), #443 (approved). Les manifestes jetables des suites sont **retirés** de `main` par commit direct après chaque preuve (`MANIFESTE_ABSENT` si on repliait dessus).
- **Le repli des APIs** (G6, ADR-085) : `POST …/promotions/{id}/rollback` (reason obligatoire ; `GATE_REFS_REQUIRED` si `RequireChangeRef || ITSMCheck` **avant** toute lecture d'historique ; `NO_PREVIOUS_STATE` 409) écrit `deploy.<env>.yaml` **verbatim N-1** dans un commit neuf (trailers + evidence), répond `restored.{environment,version,commit}` ; `Jenkinsfile.rollback` re-applique sur le clone post-revert, terminus par position, smoke = état relu. Pas de `job.xml` (from-SCM posé à la main).
- **Le formulaire humain** (A0, `Jenkinsfile.app-request`) : `properties([parameters([…])])` posé au premier stage depuis un script de choix fail-closed (`FORMULAIRE_VIDE`), `FORM_BOOTSTRAP` capturé avant, identité `jenkins-form:<uid>` par `UserIdCause`, script appelé sous `withCredentials(GITEA_CREDENTIALS_ID)` avec `set +x`, valeurs de formulaire passées par `withEnv` (fait Jenkins A0). Coquille XML sans propriété (`setup-provision-jobs.sh`, `BOOTSTRAP_JOBS` amorce le formulaire).
- **Les suites qui regardent ces fichiers** (totaux à re-mesurer avant modification) : `test-a0-wiring.sh` 176, `test-provision-apply-wiring.sh` 142, `test-provision-apply-a2.sh` 148, `test-provision-apply-a4.sh` 133, `test-selfservice-palier-a3.sh` 177, `test-selfservice-api-gate-a5.sh` 48, `test-pr-comment.sh` 41, `make lint-ci` [14/14] (compile **tous** les `ci/Jenkinsfile*` par glob).

## Décisions

### D0 — Le site : un script de demande de repli, une coquille Jenkins, zéro changement en aval

**`scripts/app-rollback-request.sh`** (nouveau, frère de `provision-request.sh`, mêmes conventions : `set -uo pipefail` sans `-e`, `REFUS: <TAG> : <phrase>` sur stderr + rc 2, token par env jamais en argv, python3 pour la forge) ouvre la PR de repli. **`ci/Jenkinsfile.app-rollback`** (nouveau, from SCM) est le formulaire humain qui l'appelle. **`ci/jenkins/app-rollback.job.xml`** est la coquille (SCM seul, aucune propriété, aucun trigger). **Aucun fichier de l'aval n'est modifié** (`Jenkinsfile.provision-apply`, `Jenkinsfile.selfservice`, `provision-apply-reconcile.sh`, `provision-apply-gate.sh`, `selfservice-palier-gate.sh`, le rôle) — hors deux commentaires (D8). C'est la preuve par construction que « le repli est un apply comme un autre ».

### D1 — L'ordre du script = la propriété (fail at the earliest, rien d'écrit avant le dernier refus)

Entrées (env) : `REQ_APP REQ_ENV REQ_REASON` (requis), `REQ_CHANGE_REF` (optionnel), `REQ_CALLER` (défaut `unknown`), `GITEA_TOKEN` (requis), `GIT_HOST GIT_REPO GIT_BASE GIT_SUBDIR MANIFEST_DIR STOA_ENV_CHAIN_FILE PROVISION_PLAN_INLINE ROLLBACK_OUT` (défauts de `provision-request.sh`).

**Le commit** : sujet `provision(<env>): repli de <app> vers l'état de la PR #<N-1> (<sha7 N-1>)`, corps = le motif, trailers `Repli-De: <sha N> (PR #<N>)`, `Repli-Vers: <sha N-1> (PR #<N-1>)`, `Repli-Motif: <motif>`, `Repli-Par: <caller>`, `Repli-Digest: <digest attendu>`, `Change-Ref: <ref>` (si fourni). **La PR** : titre `provision(<env>): <app> — repli vers #<N-1>`, corps : le marqueur, la lignée (les deux PR, leurs SHA), ce qui est restauré (ligne du palier **montrée**, cert oui/non), le digest attendu après apply (« à comparer à la ligne “digest du manifeste effectif” du rapport de provision-apply »), le `change_ref` s'il y en a un, le rappel que **toutes les portes du palier s'appliquent** et que rien n'est désinscrit. **Sorties** : `PR_URL=…`, `REPLI_DE=… REPLI_VERS=… REPLI_DIGEST=…` sur stdout ; `ROLLBACK_OUT` (KEY=VALUE, si posé) pour le Jenkinsfile.

### D2 — Le formulaire : `ci/Jenkinsfile.app-rollback`, quatre champs, la chaîne entière

`agent any`, pas de `triggers`, pas de bloc `parameters{}` : le formulaire est posé au premier stage par `properties([parameters([string APP, choice ENV, string REASON, string CHANGE_REF])])` (motif A0 : `FORM_BOOTSTRAP` lu **avant** `properties()`, refus `FORMULAIRE_VIDE` si la chaîne ne se lit pas — rien n'est posé). La liste `ENV` vient de `env_chain` **entière** (après `env_chain_validate`), calculée par un `sh` d'une ligne sur la lib (pas de nouveau script de choix : une seule liste). Identité `jenkins-form:<uid>` par `UserIdCause` (le piège `userId` nul d'A0 repris). Stage « Ouvrir la PR de repli » : `withCredentials([string(GITEA_CREDENTIALS_ID → GITEA_TOKEN)])`, `withEnv` des quatre valeurs (fait Jenkins A0 : `EnvVars.resolve`), `dir('poc-control-plane-federation') { sh 'set +x; bash scripts/app-rollback-request.sh' }`. `displayName` = `repli <app>/<env> (par <uid>)`, la description du build = `PR_URL` relue de `ROLLBACK_OUT`. Points de config client `GIT_HOST GIT_REPO GITEA_CREDENTIALS_ID` (motif `env.X ?: défaut`).

**`ci/jenkins/app-rollback.job.xml`** : coquille SCM (`CpsScmFlowDefinition`, `*/main`, `scriptPath = poc-control-plane-federation/ci/Jenkinsfile.app-rollback`, `lightweight=false`), **aucune** propriété. ### D3 — Ce que l'aval fait, sans changer : la trace du repli

La PR de repli est une PR `provision/<app>-<env>` comme les autres : `provision-plan` la commente, le merge (par un humain, portes de la chaîne) déclenche `provision-apply`, qui réconcilie (`RECONCILE_OK`, périmètre = manifeste + cert, digest mergé == main puisque **c'est** main), joue la porte A4 avant la pause, réveille le valideur, rejoue la porte au dispatch, dispatche `selfservice-app-deploy` au `MERGE_SHA` de la PR de repli, confronte `APPLIED_SHA`, et **rapporte sur la PR** « référence appliquée » + « digest du manifeste effectif » — ce digest **est** celui que la PR de repli annonçait (`Repli-Digest`) : la trace Git de l'acte est le commit de merge (sujet Gitea `… from provision/<app>-<env> into main`, trailers du commit de branche) et le rapport de PR. Verify relit `API_AT_PALIER_CONFIRMED`, `SUBSCRIPTION_CONFIRMED (id=GUID)`, `CERT_NAME_CONFIRMED`, `ENFORCEMENT_CONFIRMED`.

**Les contre-épreuves du GOAL tombent gratuitement** : « rollback vers un SHA dont l'API n'est plus au palier » ⇒ le rôle (porte A5 §1) refuse `API_NOT_PROMOTED`/`API_INACTIVE` **avant la première écriture**, relayé jusqu'à la PR de repli (« rien n'a été écrit ») ; « rollback au terminus sans référence ITSM » ⇒ `GATE_REFS_REQUIRED` **à la demande** (D1 #3, aucune PR) et, par défense en profondeur, `provision-apply-gate.sh` sur le manifeste mergé si une PR de repli était ouverte à la main sans `change_ref`.

### D9 — Limites et dettes, écrites d'avance

- **État déclaré, pas servi** (hypothèse 3) : la PR de repli restaure ce que la PR N-1 a mergé, même si son apply avait été refusé ; les portes rejouent. Un registre « appliqué » dans Git serait une décision de forme contraire au GOAL :116 — nommé, pas fait.
- **Merge style** : la clé de lignée est le sujet du merge commit Gitea ; squash/rebase la perdent (`AUCUNE_LIGNEE`, jamais un faux N-1).
- **`REQUESTER_UNKNOWN` sur `int`+** tant qu'A7 n'ouvre pas les PR sous identité humaine — le repli en `rec` est la porte du GOAL, le terminus est prouvé jusqu'à `GATE_REFS_REQUIRED`/`AUCUNE_LIGNEE`.
- **Mono-gateway** : « état au SHA N-1 » se lit sur la 10.15 unique ; la topologie par palier est celle du client.
- **La suspension** (règle 2) n'est pas écrite : `isSuspended` n'existe nulle part dans le rôle — le verbe de retrait est un jalon à part (hors GOAL A0..A7), nommé dans l'ADR.
- **Le levier direct** (D8) reste : un `MERGE_SHA` de la lignée saisi sur l'aval passe A3 et le rôle, pas les portes A4 — propriété A2, pas d'A6.
- **Le repli d'un cert absent à N-1** supprime le fichier ; le rôle relit `public_cert_ref` absent ⇒ pas de cert — la rotation `overlap` (A1) n'est pas rejouée en repli (le repli est `replace` par nature : ligne verbatim).
- **`change_ref` remplacé, `pv_ref` gardé** : le PV de N-1 atteste sa recette d'alors ; un client qui exige un PV **du repli** ajoute `pv_ref` au formulaire (un champ, même mécanisme).
