# A6 — Le repli : re-convergence à l'état N-1, sans changer de clé

## Porte (reprise du GOAL, non négociable)

- **Porte A6 :** deux applies successifs de la même application ⇒ **même GUID d'application, même clé** ; rollback rec ⇒ état de la gateway = état au SHA N-1 (identifiers, IP, cert), **vérifié par lecture, pas par log**.
- **Contre-épreuve :** rollback vers un SHA dont l'API n'est plus au palier ⇒ `API_NOT_PROMOTED` (A5 tient aussi en repli) ; rollback au terminus sans référence ITSM ⇒ refus (le motif G6).
- **Deux règles mesurées (spike S1, 2026-09-02), non négociables :** (1) la chaîne **ne désinscrit jamais** (`DELETE …/apis` sur une paire qui a servi est irréversible en 10.15) — un repli re-converge identifiers et policy, jamais la souscription ; (2) le **retrait** d'une application est une **suspension** (`isSuspended`), pas une désinscription.

## La thèse, en une phrase

Le GOAL dit « on promeut la **demande**, pas l'objet ». Alors **on replie la demande** : le repli d'une application au palier est une **PR de repli** `provision/<app>-<env>` dont la ligne `per_env.<env>` et le certificat `certs/<app>-<env>.crt` redeviennent, **à l'octet**, ceux du SHA de merge **précédent** (N-1) de cette même branche. Puis la chaîne existante — merge (ADR-081) → `provision-apply` (portes A4 deux fois, pause nominative) → `selfservice-app-deploy` (garde A3, rôle avec porte A5, verify) — l'applique **comme tout apply**. Rien de nouveau en aval ; le verbe est la convergence idempotente (spike S1 : 4822/0, GUID et clé stables), donc l'application garde son GUID et sa clé.

C'est le port exact d'**ADR-085** : G6 ne re-appliquait pas un vieux commit, il écrivait le contenu N-1 de `deploy.<env>.yaml` **verbatim dans un commit NEUF sur main**, puis re-appliquait ce commit. Pour les applications, « le fichier de déploiement du palier » est la PR (GOAL :116, décision de forme) — le commit neuf est donc une PR.

## Hypothèses (session autonome — ce qu'un humain aurait tranché)

1. **Le repli est une PR, pas un re-dispatch direct du SHA N-1** (le « levier » annoncé par `ci/Jenkinsfile.selfservice:194` et `ENVIRONNEMENTS.md:1038` : un `MERGE_SHA` saisi à la main sur l'aval). Cinq raisons, dans l'ordre de poids : (a) **`PALIER_SUPPLANTE`** (A2, `provision-apply-reconcile.sh:269-276`) refuse structurellement de re-projeter un état dépassé — rejouer le webhook de N-1 est refusé, et c'est juste : le repli n'est pas une exception à cette règle, c'est un état **nouveau** sur `main` dont le contenu est celui de N-1 ; (b) **la lignée du rôle** : un re-apply du SHA N-1 checkoute l'arbre entier d'alors (rôle, lib, gardes d'alors — la limite écrite en A5-D7 et ADR-088 :65) ; la PR de repli est appliquée à **son** SHA de merge, arbre d'aujourd'hui — la limite A5-D7 **se dissout** au lieu d'exiger un « plancher de SHA » ; (c) **Git redevient la vérité** après le repli (le dernier merge de `provision/<app>-<env>` dit ce que la gateway sert), et le rejeu d'un webhook ancien ne défait pas le repli en silence ; (d) **toutes les portes s'appliquent sans une ligne de code** — quatre yeux, `deployerGroup`, refs, ITSM, terminus par position, A5 ; (e) le motif G6 (commit neuf, contenu N-1). Coût assumé : un merge humain de plus qu'un job direct — en `rec` (`selfApproval`) le demandeur merge lui-même, en `int`+ c'est le quatre-yeux que DORA art. 17(1)(b) exige de **tout** changement, repli compris (G6 a gardé le `change_ref` au rollback pour la même raison). Le levier direct n'est **pas retiré** par A6 (c'est la propriété A2 « un SHA de la lignée est accepté ») mais **renommé** : ce n'est pas le repli, c'est un rejeu hors chaîne borné par A3 — les deux commentaires sont réécrits (D8).
2. **N et N-1 sont définis par la LIGNÉE de la branche, lue sur la forge et ordonnée par Git** (amendé — critique de chaîne n°5 : le sujet du merge commit est un gabarit de forge, remplaçable ; la lignée ne doit dépendre d'aucun gabarit). **Forge = la vérité sur les PR** : toutes les PR fermées du dépôt (`GET /pulls?state=closed`, paginé jusqu'à la page vide — Gitea 1.22 n'a pas de filtre `head`), retenues si `merged` est vrai, `head.ref` == `provision/<app>-<env>` **exactement** (jamais un préfixe), `base.ref` == `GIT_BASE`, `merge_commit_sha` hexadécimal ; une PR mergée **depuis un fork** (`head.repo.full_name` ≠ `GIT_REPO`) avec ce `head.ref` est une lignée que personne n'a voulue ⇒ **`LIGNEE_AMBIGUE`** (fail-closed, jamais exclue en silence — critique sécurité n°2). **Git = la vérité sur main** : chaque `merge_commit_sha` doit être sur la première parenté de `main` (`git rev-list --first-parent`), et c'est **sa position** qui ordonne — un `merge_commit_sha` de PR mergée absent de la première parenté est une incohérence forge/Git (réécriture d'historique, base changée) ⇒ **`FORGE_INCOHERENTE`**, jamais ignoré en silence. **La lignée est bornée à la vie courante du manifeste** (critique de chaîne n°3 : les suites retirent des manifestes par commit direct sur `main` et une application recréée sous le même nom hériterait d'une vie antérieure) : `BIRTH` = le dernier commit de la première parenté qui **ajoute** le manifeste (`git log --first-parent --diff-filter=A -1 -- <manifeste>`) ; seuls les merges dont `BIRTH` est ancêtre-ou-égal comptent. N = le plus récent, N-1 = le précédent. Sans N ⇒ `AUCUNE_LIGNEE` ; sans N-1 ⇒ `AUCUN_ETAT_PRECEDENT` (le `NO_PREVIOUS_STATE` 409 de G6) — remède nommé : le retrait est une suspension, pas un repli. Ce choix marche aussi en squash/rebase (le commit de squash **est** `merge_commit_sha`, sur la première parenté) : la limite « style de merge » disparaît.
3. **Le repli restaure l'état DÉCLARÉ N-1 (Git), pas l'état SERVI.** Aucune trace machine « appliqué » n'existe dans Git pour les applications (GOAL :116 ; le SHA appliqué ne vit que dans le commentaire de PR et les `buildVariables`) — A6 n'invente pas de registre. Un N-1 mergé puis **refusé à l'apply** (lignée réelle `provision/a4p1788394281-int` : #433, #435, #437 jamais projetées, #439 projetée) est restauré tel que déclaré et **repasse toutes les portes** ; la PR de repli cite la lignée et le digest attendu pour que le mergeur voie ce qu'il restaure. Garde de cohérence : `digest(main, env) == digest(N, env)` sinon **`REFERENCE_DIVERGENTE`** (quelqu'un a écrit `main` hors PR — le repli ne raisonne pas sur un état qu'aucune PR ne porte).
4. **L'application et le palier SONT saisis** (formulaire) — contrairement à G6-D1 — parce que la paire (app, env) **est** l'identité du fichier de déploiement (la branche) ; il n'y a pas d'autre poignée (pas d'objet « promotion »). Tout le reste — N, N-1, digest, ligne, cert — est **dérivé, jamais saisi**. La liste des paliers du formulaire est la **chaîne entière**, terminus compris : le repli est d'abord un geste de terminus, et c'est la seule voie d'application qui le nomme — les portes décident (`GATE_REFS_REQUIRED` à la demande, puis A4 : `REQUESTER_UNKNOWN`, ITSM, `TERMINUS_SANS_VOIE` jusqu'à A7). Sur ce lab, aucune application ne déclare `per_env.<terminus>` (la demande l'exclut par structure) : un repli au terminus s'arrête à `PALIER_ABSENT` après la porte — ce que la contre-épreuve mesure.
5. **`change_ref` : exigé à la DEMANDE de repli si la porte du palier l'exige** (`env_chain_gate` ⇒ `GATE=1|…`, c'est-à-dire `requireChangeRef || itsmCheck` — le prédicat de G6-D3 et de `provision-apply-gate.sh:181`) ⇒ `GATE_REFS_REQUIRED` **au plus tôt**, avant tout clone et tout appel de forge, aucune PR ouverte. Fourni, il **remplace ou ajoute** `change_ref` dans la ligne restaurée (G6-D4 : un vrai ITSM a passé le change de N-1 à « implemented », un repli d'urgence porte **son** change). **La ligne candidate (N-1 ⊕ `change_ref`) est construite en mémoire AVANT tout autre verdict** — c'est elle, pas la ligne brute de N-1, que `ETAT_IDENTIQUE` et l'auto-vérification comparent (critique de chaîne n°1, **bloquant** : sur gitea `a4p1788394281-prod` #442/#443 ne diffèrent que par `change_ref` ; comparer la ligne brute puis substituer produisait un commit vide sur tout palier gaté). Le remplacement est **textuel** (l'octet du reste de la ligne est préservé) mais **vérifié sur le mapping** : la paire `change_ref: <scalaire>` est reconnue sous ses trois formes (`"…"`, `'…'`, nue), remplacée si présente, insérée avant l'accolade fermante sinon ; puis la ligne finale doit porter **exactement une** occurrence de `change_ref:` et se relire (`BaseLoader`) avec `change_ref == REQ_CHANGE_REF` — sinon **`REF_DUPLIQUEE`** (critique de chaîne n°2 : PyYAML avale une clé dupliquée sans erreur, et l'auto-vérification de la lib compare deux parses du **même** texte). **`pv_ref` n'est jamais exigé ni touché** (G6-D3 : le PV atteste la recette de l'état qu'on quitte ; l'état restauré a porté le sien). Sans `CHANGE_REF` fourni et sans exigence : ligne **verbatim**.
6. **La racine du manifeste ne bouge pas.** A1 la fige (`CONTRAT_DIVERGENT`) ; si elle diffère entre N-1 et N (édition hors flux), refus **`RACINE_DIVERGENTE`** — la restaurer toucherait les autres paliers. Le repli ne raisonne que sur la ligne `per_env.<env>` et le cert du palier. La contre-vérification est gratuite : `app_manifest_digest_env` (racine ⊕ `per_env.<env>`) sur l'arbre de la PR de repli **doit** égaler le digest attendu, calculé **par la même lib** sur une copie du manifeste de N-1 où la même ligne candidate a été fusionnée — sinon `RESTAURATION_INFIDELE`, rien n'est poussé.
7. **Périmètre de la PR de repli = son manifeste + son certificat** (A2 `PR_HORS_PERIMETRE` le tient déjà). Le cert `clients/provisioned/certs/<app>-<env>.crt` est restauré **à l'octet** : présent à N-1 ⇒ `git show N-1:…`, absent à N-1 et présent à N ⇒ **supprimé** dans la PR, absent des deux ⇒ rien. Limite mesurée (critique des preuves n°5, écrite en D9) : le rôle **préserve** toute dimension d'identifier absente du manifeste (`main.yml:340-348`) et verify saute le bloc cert quand `public_cert_ref` est vide (`verify.yml:98-99`) — un repli vers « sans cert » retire le fichier de Git mais **laisse le cert de N sur la gateway** ; A6 ne touche pas le rôle et le dit.
8. **Identité : la PR de repli est ouverte par le token `ci`** (comme `provision-request.sh`, la voie livrée) ; le demandeur du repli (`jenkins-form:<uid>`, le motif d'`app-request` — `jenkins-form:anonymous` sur un déclenchement anonyme) est dans le commit (trailer `Repli-Par`) et le corps de la PR, **à titre informatif** : rien de sécuritaire n'en dérive. Sur `int`+ la porte A4 refuse `REQUESTER_UNKNOWN` tant qu'A7 n'ouvre pas les PR sous identité humaine — le repli **hérite** la limite et la lève avec A7 sans changement (même mécanisme d'ouverture de PR à faire évoluer).
9. **« Même GUID, même clé » est une propriété de la convergence, vérifiée par LECTURE**, avec un jeu de champs **fixé** (critique des preuves n°1, **bloquant** : une empreinte « identifiers + clé » est contradictoire — les identifiers **doivent** changer entre N-1 et N — et instable — wM recrée les identifiers à chaque PUT, `id`/`lastupdated` bougent) : sur `GET /applications/{id}` (l'objet, pas la liste), **GUID** = `id` ; **KEY** = sha256 de `accessTokens.apiAccessKey_credentials.apiAccessKey` (jamais imprimée, ni la clé ni l'empreinte en clair dans un journal partagé — comparée en mémoire par le harnais) ; **IDS** = JSON canonique de `[(key, name, sorted(value))]` restreint à `{httpsCertificate, ipAddressRange, openIdClaims, token}` — exactement `ss_ids_now` du rôle (`main.yml:370-379`) ; **SUBS** = `sorted(consumingAPIs)` ; `isSuspended`. Verify relit en plus `SUBSCRIPTION_CONFIRMED (id=<GUID>)` (A5-D3) et `CERT_NAME_CONFIRMED`. Le rôle n'apprend rien : A6 ne touche ni `main.yml` ni `verify.yml`. Rien n'est désinscrit (règle 1) ; A6 n'écrit pas la suspension (règle 2 — verbe de retrait, `isSuspended` n'existe nulle part dans le rôle ; nommé en D9).
10. **Le repli est une pile de profondeur 1, et le repli du repli restaure N** : la lignée est linéaire, la PR de repli R est un merge de `provision/<app>-<env>` comme les autres, donc « replier R » restaure N (l'état d'avant R) — jamais N-2 (critique de chaîne n°6). Pas de 409 « double rollback » comme G6 (qui recyclait un marqueur). **Nommé, pas caché** : quand le commit de branche de N porte le trailer `Repli-Vers:`, la demande imprime et écrit dans la PR `REPLI_DU_REPLI : restaure #N-1, l'état d'avant le repli #N ; si l'apply de #N a été REFUSÉ, le remède est le rejeu du webhook de #N (A2), pas ce repli`.

## Décisions

### D0 — Le site : un script de demande de repli, une coquille Jenkins, une garde symétrique dans la demande, zéro changement en aval

**`scripts/app-rollback-request.sh`** (nouveau, frère de `provision-request.sh`, mêmes conventions : `set -uo pipefail` sans `-e`, `REFUS: <TAG> : <phrase>` sur stderr + rc 2, token par env jamais en argv, python3 pour la forge) ouvre la PR de repli. **`ci/Jenkinsfile.app-rollback`** (nouveau, from SCM) est le formulaire humain qui l'appelle. **`ci/jenkins/app-rollback.job.xml`** est la coquille (SCM seul, aucune propriété, aucun trigger). **`scripts/provision-request.sh`** gagne **une** garde additive (D1bis). **En aval, un seul ajout, conditionnel au trailer d'un commit de repli** : `provision-apply-reconcile.sh` §4 (`REPLI_PERIME`, D1ter) — inerte pour toute PR qui n'est pas un repli. Rien d'autre ne change (`Jenkinsfile.provision-apply`, `Jenkinsfile.selfservice`, `provision-apply-gate.sh`, `selfservice-palier-gate.sh`, le rôle) — hors deux commentaires (D8). C'est la preuve par construction que « le repli est un apply comme un autre ».

### D1bis — La garde symétrique : une demande ne réécrit pas une PR de repli ouverte

`provision-request.sh` pousse **en force** la branche `provision/<app>-<env>` **avant** de chercher une PR ouverte (`:547-577` puis `:601-603`) : une demande émise pendant qu'une PR de repli est ouverte réécrirait **son** contenu — le corps garderait « repli », le HEAD serait la demande (critique de chaîne n°4). Garde additive, **avant le push** de la demande : `GET /pulls?state=open` filtré `head.ref` == branche et même dépôt ; si une PR **d'un login de service** a pour commit de tête un message portant le trailer `Repli-Vers:` (relu par `GET /repos/…/git/commits/<head.sha>` — jamais le corps de la PR) ⇒ `REFUS: REPLI_EN_COURS : la PR #n est un repli ouvert sur provision/<app>-<env> — la merger ou la fermer avant une nouvelle demande` (rc 2, rien poussé). Le push de la demande passe de `--force` à `--force-with-lease` sur la tête relue par son `fetch` existant (`:557`). C'est le seul fichier **amont** existant que touche A6 ; les suites `test-app-request-v*.sh` et `test-a0-wiring.sh` sont rejouées.

### D1ter — La fenêtre entre la PR de repli et son merge : `REPLI_PERIME` au réconciliateur (le seul ajout en aval, conditionnel)

`PALIER_SUPPLANTE` compare `digest(MERGE_SHA)` à `digest(main)` : pour la PR qui **vient** d'être mergée les deux sont le même commit — il ne dit rien si `main` a bougé pour ce palier **entre** l'ouverture de la PR de repli et son merge (un commit direct, une PR humaine ne touchant que le cert ; critique sécurité n°3). Le seul site qui tient cette fenêtre est le réconciliateur, au merge : `provision-apply-reconcile.sh` §4 gagne un bloc **conditionnel** — si `MERGE_SHA` a un second parent et que son message porte `Repli-De: <sha>`, alors `digest(MERGE_SHA^1, env)` doit égaler `digest(<sha Repli-De>, env)` **et** le cert de `MERGE_SHA^1` celui de `<sha>` à l'octet ; sinon **`REPLI_PERIME`** (« main a bougé pour <app>/<env> entre la demande de repli et son merge — rejouer la demande de repli »), commenté sur la PR comme les autres refus du réconciliateur, **avant la pause**. Sans trailer (toute PR d'aujourd'hui, un squash), le bloc est inerte : le réconciliateur est **inchangé à l'octet** hors ce bloc (asserté). Mécanisme de forge équivalent, non posé sur le lab : `block_on_outdated_branch` de la protection de `main` (`lib/repo-protection.sh`, knob client) — il bloquerait aussi toute demande dont la base a bougé, ce que les suites du lab ne supporteraient pas (D9).

### D2 — Le formulaire : `ci/Jenkinsfile.app-rollback`, quatre champs, la chaîne entière

`agent any`, pas de `triggers`, pas de bloc `parameters{}` : le formulaire est posé au premier stage par `properties([parameters([string APP, choice ENV, string REASON, string CHANGE_REF])])` (motif A0 : `FORM_BOOTSTRAP` lu **avant** `properties()`, refus `FORMULAIRE_VIDE` si la chaîne ne se lit pas — rien n'est posé). La liste `ENV` vient de `env_chain` **entière** (après `env_chain_validate`), calculée par un `sh` d'une ligne sur la lib (pas de nouveau script de choix : une seule liste) — elle diverge volontairement du `choice ENVIRONMENT` de l'aval (`env_chain_nonprod`) : la porte refuse avant tout dispatch. Identité `jenkins-form:<uid>` par `UserIdCause` (le piège `userId` nul d'A0 repris : `anonymous`). Stage « Ouvrir la PR de repli » : `withCredentials([string(GITEA_CREDENTIALS_ID → GITEA_TOKEN)])`, `withEnv` des quatre valeurs (fait Jenkins A0 : `EnvVars.resolve`), `dir('poc-control-plane-federation') { sh 'set +x; STOA_ENV_CHAIN_FILE="$WORKSPACE/poc-control-plane-federation/clients/_example/environments.yaml" bash scripts/app-rollback-request.sh' }` — la chaîne **épinglée sur la ligne d'appel**, comme sur celle qui calcule la liste `ENV`. `displayName` = `repli <app>/<env> (par <uid>)`, la description du build = `PR_URL` relue de `ROLLBACK_OUT`. Points de config client `GIT_HOST GIT_REPO GITEA_CREDENTIALS_ID` (motif `env.X ?: défaut`).

**`ci/jenkins/app-rollback.job.xml`** : coquille SCM (`CpsScmFlowDefinition`, `*/main`, `scriptPath = poc-control-plane-federation/ci/Jenkinsfile.app-rollback`, `lightweight=false`), `<properties/>` et `<triggers/>` **vides**. Pose : `JOBS=app-rollback BOOTSTRAP_JOBS=app-rollback scripts/setup-provision-jobs.sh` (le build d'amorçage matérialise le formulaire, fait A0). Le pipeline se met à jour par `git push gitea main`.

### D3 — Ce que l'aval fait, sans changer : la trace du repli

La PR de repli est une PR `provision/<app>-<env>` comme les autres : `provision-plan` la commente, le merge (par un humain, portes de la chaîne) déclenche `provision-apply`, qui réconcilie (`RECONCILE_OK`, périmètre = manifeste + cert, digest mergé == main puisque **c'est** main), joue la porte A4 avant la pause, réveille le valideur, rejoue la porte au dispatch, dispatche `selfservice-app-deploy` au `MERGE_SHA` de la PR de repli, confronte `APPLIED_SHA`, et **rapporte sur la PR** « référence appliquée » + « digest du manifeste effectif » — ce digest **est** celui que la PR de repli annonçait (`Repli-Digest`) : la trace Git de l'acte est le commit de merge et les trailers du commit de branche, plus le rapport de PR. Verify relit `API_AT_PALIER_CONFIRMED`, `SUBSCRIPTION_CONFIRMED (id=GUID)`, `CERT_NAME_CONFIRMED`, `ENFORCEMENT_CONFIRMED`.

**Les contre-épreuves du GOAL tombent gratuitement** : « rollback vers un SHA dont l'API n'est plus au palier » ⇒ le rôle (porte A5 §1) refuse `API_NOT_PROMOTED`/`API_INACTIVE` **avant la première écriture**, relayé jusqu'à la PR de repli (« rien n'a été écrit ») ; « rollback au terminus sans référence ITSM » ⇒ `GATE_REFS_REQUIRED` **à la demande** (D1 #3, aucune PR) et, par défense en profondeur, `provision-apply-gate.sh` sur le manifeste mergé si une PR de repli était ouverte à la main sans `change_ref`.

### D9 — Limites et dettes, écrites d'avance

- **État déclaré, pas servi** (hypothèse 3) : la PR de repli restaure ce que la PR N-1 a mergé, même si son apply avait été refusé ; les portes rejouent. Un registre « appliqué » dans Git serait une décision de forme contraire au GOAL :116 — nommé, pas fait.
- **Profondeur 1** (hypothèse 10) : jamais N-2 ; « replier un repli mergé mais refusé à l'apply » restaure ce que la gateway sert déjà — la PR le dit (`REPLI_DU_REPLI`), le remède est le rejeu du webhook (A2). Une profondeur saisie (`REQ_DEPTH`) serait un champ de plus, hors A6.
- **Le cert de N reste sur la gateway après un repli vers « sans cert »** (hypothèse 7) : le rôle préserve les dimensions absentes du manifeste et verify les ignore — dette du rôle, nommée dans l'ADR ; A6 retire le fichier de Git et le dit dans la PR.
- **`REQUESTER_UNKNOWN` sur `int`+** tant qu'A7 n'ouvre pas les PR sous identité humaine — le repli en `rec` est la porte du GOAL, le terminus est prouvé jusqu'à `GATE_REFS_REQUIRED`/`PALIER_ABSENT`.
- **Mono-gateway** : « état au SHA N-1 » se lit sur la 10.15 unique ; la topologie par palier est celle du client.
- **La suspension** (règle 2) n'est pas écrite : `isSuspended` n'existe nulle part dans le rôle — le verbe de retrait est un jalon à part (hors GOAL A0..A7), nommé dans l'ADR.
- **Le levier direct** (D8) reste : un `MERGE_SHA` de la lignée saisi sur l'aval passe A3 et le rôle, pas les portes A4 — propriété A2, pas d'A6.
- **La liste `ENV` du formulaire** (chaîne entière) diverge de celle de l'aval (hors terminus) : voulu, la porte refuse avant tout dispatch.
- **La chaîne est lue dans le workspace** du job (le `main` du checkout SCM), pas épinglée sur un clone (A4 l'épingle pour `provision-apply`) : un repli n'est pas un dispatch, et la porte A4 rejoue la lecture épinglée au merge.
- **La rotation `overlap`** (A1) n'est pas rejouée en repli : la ligne est verbatim, le repli est `replace` par nature.
- **`change_ref` remplacé, `pv_ref` gardé** : le PV de N-1 atteste sa recette d'alors ; un client qui exige un PV **du repli** ajoute `pv_ref` au formulaire (un champ, même mécanisme).
- **Pagination forge** : `state=closed` est parcouru en entier à chaque repli (~9 pages sur le lab) — un dépôt de milliers de PR paie quelques secondes ; Gitea ≥ 1.23 offrirait un filtre `head`, non requis.
- **La fenêtre PR de repli → merge** est tenue par `REPLI_PERIME` (D1ter) au merge, pas avant : le plan (`provision-plan`) ne se rejoue pas quand `main` bouge — un plan « repli périmé » serait du théâtre. Le knob de forge `block_on_outdated_branch` (client) la fermerait mécaniquement pour **toute** PR ; non posé sur le lab (les suites enchaînent des merges).
- **La branche `provision/*` n'est pas protégée** (seul `main` l'est) : quiconque écrit sur le dépôt peut y pousser ; c'est pourquoi `EXIST` se décide sur l'auteur **et** le contenu, jamais sur un marqueur, et pourquoi la tête distante est relue et prise en bail.
