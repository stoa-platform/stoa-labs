# A2 — La référence de déploiement d'une application

## Porte (reprise du GOAL, non négociable)

- **Porte :** merger `provision/<app>-rec`, pousser un autre commit sur `main` **avant** de répondre à la pause ⇒ l'apply projette le **SHA mergé**, pas `HEAD`.
- **Contre-épreuve :** webhook forgé sur une PR **jamais mergée** ⇒ `PAYLOAD_PERIME` (le motif G7 #25, rejoué sur cette voie) ; gateway inchangée.
- La PR reçoit en commentaire le **SHA appliqué** et le **digest du manifeste effectif du palier** (`per_env.<env>` fusionné sur la racine) — la réponse à « qu'est-ce qui tourne en rec ? ».
- Décision de forme (GOAL) : pas de branche d'environnement, pas de `deploy.<env>.yaml` pour les applications — la PR `provision/<app>-<env>` **est** le fichier de déploiement du palier, son SHA de merge est la référence.

## Décisions

### D1 — `provision-apply` sort du XML : Jenkinsfile déclaratif from SCM (A0, périmètre = le job qu'A2 touche)

A2 doit modifier `provision-apply` (capter `MERGE_SHA`, le passer, réconcilier). La contrainte utilisateur du GOAL — **aucun `job.xml` porteur de logique** — interdit d'ajouter ces lignes au Groovy inline : « la dette cesse d'être sans urgence le jour où l'on bâtit dessus ». Le job est donc converti **maintenant**, sur le modèle exact de `team-apply` :

- `ci/Jenkinsfile.provision-apply` (déclaratif, `agent none`, `disableConcurrentBuilds`), `ci/jenkins/provision-apply.job.xml` réduit à la **coquille** `CpsScmFlowDefinition` (`http://gitea:3000/ci/stoa-labs.git`, `*/main`, `scriptPath poc-control-plane-federation/ci/Jenkinsfile.provision-apply`, `lightweight=false`) + **miroir** du bloc `triggers` — **7 clés** (`MERGE_SHA` = `$.pull_request.merge_commit_sha` ajoutée), token `stoa-provision-apply`, filtre `^closed\|true$` inchangés ; **aucun `<script>`**.
- Un premier stage **sans agent** « Contexte du webhook » nomme le build (`apply <app>/<env> (PR #n)` — format lu par la suite live — ou `hors provision/* (PR #n)`) ; les deux stages suivants sont gardés par `when { beforeAgent true / beforeInput true ; PR_BRANCH startsWith 'provision/' }` : une PR étrangère (onboard/*, docs, promotion) **n'alloue aucun agent, n'appelle pas Gitea, ne commente rien, sort verte** — le `return` du Groovy est conservé. Le script de réconciliation, lui, reste fail-closed sur toute branche hors `provision/*` (`BRANCH_FORMAT_INVALIDE`) : c'est le pipeline qui filtre, le script qui refuse.
- `provision-plan` et `provisioning-request` restent en Groovy inline : le reste d'A0, indépendant.
- Volontairement **pas de bloc `parameters {}`** de niveau pipeline : ces valeurs ne viennent que du webhook.
- `setup-provision-jobs.sh` (POST `config.xml`, historique conservé) re-pose la coquille ; son en-tête est corrigé.

### D2 — Réconciliation **avant** la pause : ni le payload ni « le dernier `main` » ne font foi

`scripts/provision-apply-reconcile.sh` (bash + python embarqué, forme de `team-promote.sh` §2), appelé par un stage **avec agent** (`agent any`, court, sans identité humaine), sous `withCredentials(gitea-provision-token)`, dans l'ordre :

1. **Forme, avant tout appel réseau** : `PR_NUMBER` `^[0-9]+$` (`PR_NUMBER_INVALIDE`), `MERGE_SHA` `^[0-9a-f]{40}$` (`MERGE_SHA_INVALIDE` — vide compris), `PR_BRANCH` ∈ `provision/<app>-<env>` (`BRANCH_FORMAT_INVALIDE` ; `app` `[a-z0-9][a-z0-9-]*`, `env` `[a-z0-9]+`, découpage au **dernier** tiret : le chemin du manifeste ne peut pas sortir de son dossier). **Une valeur refusée n'est jamais recopiée** dans un message : le journal la montre tronquée à 80 caractères et échappée (`printf %q`), le commentaire (s'il y en a un) nomme le champ et la classe attendue.
2. **Gitea = la vérité sur la PR** : `GET /repos/<GIT_REPO>/pulls/<PR_NUMBER>` ; les champs attendus doivent être **présents** (`merged`, `merge_commit_sha`, `head.ref`, `base.ref`, `user` — un 200 sans eux, portail interposé ou autre objet, est `GITEA_RECONCILE_ECHEC`, pas une divergence) ; puis `merged === true` **et** `merge_commit_sha == MERGE_SHA` **et** `head.ref == PR_BRANCH` **et** `base.ref == main` — toute divergence ⇒ `PAYLOAD_PERIME` ; échec d'appel / JSON illisible ⇒ `GITEA_RECONCILE_ECHEC` ; `merged_by.login` vide ⇒ `MERGER_UNKNOWN` ; saut de ligne dans un login ou `head.ref` ⇒ `GITEA_RECONCILE_ECHEC`.
3. **Périmètre de la PR** : `GET /pulls/<n>/files` ⊆ {`poc-control-plane-federation/clients/provisioned/applications/<app>.ansible.yml`, `…/certs/<app>-<env>.crt`} sinon `PR_HORS_PERIMETRE` (vide ⇒ idem) — l'aval checkoute l'arbre **entier** au SHA mergé : une PR qui éditerait le rôle ou un script s'exécuterait sous l'identité du valideur. Style de merge indifférent (`/files` couvre merge, squash, rebase).
4. **Git = la vérité sur `main`** (dans le workspace, `git fetch -q origin main`) : `merge-base --is-ancestor MERGE_SHA origin/main` sinon `MERGE_SHA_NON_ANCETRE` ; le manifeste doit exister au SHA mergé **et** sur `main` (`MANIFESTE_ABSENT`) ; le palier doit être déclaré au SHA mergé (`PALIER_ABSENT`, via la lib) ; et le **digest du manifeste effectif du palier** (D4) au SHA mergé doit être **égal** à celui de `origin/main` — sinon **`PALIER_SUPPLANTE`** : main porte un état plus récent de ce palier que cette PR (rejeu d'un webhook ancien, « Redeliver » Gitea) ; on ne re-projette jamais un état dépassé — rejouer une demande, ou le repli A6. Granularité = **le palier** : une PR `foo-dev` postérieure ne bloque pas le rejeu légitime de `foo-rec` ; un reformatage de `main` sans changement de fond non plus. **La porte A2 tient** : le commit direct sur `main` qui la constitue arrive APRÈS la réconciliation (pendant la pause), et l'aval projette le SHA mergé.
5. **Sortie** : `RECONCILE_OUT` (`GITEA_MERGED_BY`, `GITEA_REQUESTER`, `APP_NAME`, `ENV_NAME`, `MANIFEST`, `MERGED_DIGEST`), chargé par `readFile` + **assignations explicites** (pas de `env."$k"` dynamique ; `readProperties` indisponible) — **ce sont ces identités**, jamais `PR_MERGED_BY`/`PR_REQUESTER` du payload, qui nourrissent `assert-merge-identity.sh` (l'écart que `team-promote.sh` nomme « à corriger chez les frères » : ici corrigé). Et `RECONCILE_FACTS` (`GITEA_HEAD_REF=<head.ref relu>`), écrit **dès la relecture, succès comme échec**, chargé par un `post{always}` de stage : c'est lui qui autorise le statut build du pipeline à parler.
6. **Commentaire de refus** : **seulement si la forge a confirmé une PR `provision/*`** (`GITEA_HEAD_REF` relu — un `PR_NUMBER` forgé ne fait pas publier le compte de service sur une PR étrangère ; refus de forme, 404, 500, JSON illisible ⇒ journal + rc 1 seulement), sous le marqueur **`<!-- provision-apply-refus -->`**, distinct de celui du résultat d'apply (D5) — un webhook forgé ne peut pas PATCHer l'enregistrement SHA/digest d'un apply réel ; corps : « CE webhook n'a rien appliqué » (jamais « l'application n'est PAS déployée », faux si un apply antérieur existe). Best-effort (`|| true`) : le rc porte le verdict.

**Pourquoi avant la pause** : réconcilier d'abord évite de **réveiller un humain** pour un payload forgé ou périmé ; le stage de pause reste **sans agent**. Une PR mergée ne se démerge pas et un SHA ne change pas ; ce qui peut changer entre la réconciliation et la réponse — `main` — est précisément ce que la porte A2 fait bouger, et l'aval projette le SHA mergé.

### D3 — Le SHA voyage en paramètre, l'aval refuse de s'en passer, et **revient confirmé**

`selfservice-app-deploy` (`ci/Jenkinsfile.selfservice`) reçoit un paramètre **`MERGE_SHA`** (`string`, défaut vide ; déclaré AUSSI dans le XML de `setup-selfservice-job.sh`, avec `ADMIN_VIA` et `DEBUG`) et un premier stage **« Référence »**, avant le PLAN :

- **`MERGE_SHA_REQUIS`** : si le build a un amont (`currentBuild.upstreamBuilds` non vide — filtre par `instanceof`, donc attrape la `BuildUpstreamCause` du step `build` ; `getBuildCauses('hudson.model.Cause$UpstreamCause')` compare le nom exact et ne la verrait PAS) et `params.MERGE_SHA` est vide ⇒ `error`, avant tout appel réseau. Un appelant amont qui n'a pas transmis la référence (paramètre non matérialisé, appelant d'avant A2) ne fait pas appliquer `HEAD` « par défaut ». PLAN par webhook, amorçage REST, voie humaine directe : sans amont, comportement d'aujourd'hui.
- `MERGE_SHA` **non vide** : forme (`MERGE_SHA_INVALIDE`) ; `git fetch -q origin main` ; `merge-base --is-ancestor` (`MERGE_SHA_NON_ANCETRE`) ; **lignée first-parent** (`git rev-list --first-parent origin/main | grep -qx` ⇒ sinon `MERGE_SHA_HORS_LIGNEE` : un commit intérieur à une branche de PR, ancêtre une fois la PR mergée, n'est pas un état atterri sur `main`) ; `git checkout -q` ; **`REF="$(git rev-parse HEAD)"` APRÈS le checkout** — jamais l'écho du paramètre ; digest (D4) fail-closed (`PALIER_ABSENT` avant tout appel gateway) ; mode `pinned`.
- `MERGE_SHA` **vide** (sans amont) : `HEAD` du checkout SCM, mode `head`, digest best-effort.
- Le stage écrit des fichiers `REFERENCE_*` ; les fichiers **`APPLIED_*`** (`.a2-applied-sha/mode/digest`) ne sont écrits qu'à la **fin du `sh` d'apply, après converge + verify** (un plan-only — sortie 0 sans identité — ou un échec n'annonce rien) et chargés dans `env.` par un `script{}` gardé par `fileExists` ; le stage Référence purge les `APPLIED_*` d'un build précédent. La définition du pipeline vient de `main` (from SCM) ; l'arbre — rôle, scripts, `ci/lib`, manifeste — est celui du SHA mergé, comme `team-apply.sh`.

Côté `provision-apply`, dans le stage de pause **sans agent** : la pause est un **`input()` scripté** dans un `script{}` (pas la directive déclarative) — **mesuré** (builds #75, #78) : depuis Jenkins 2.236 `PasswordParameterValue` exige un `hudson.util.Secret`, une String d'environnement lève `ClassCastException` et `Secret.fromString` n'est pas permis dans le sandbox ; l'`input()` scripté rend le Secret tel quel (ce que faisait le Groovy d'origine) et il ne traverse que Groovy — seul `V_USER` entre dans l'environnement des deux `sh` (`withEnv(["V_USER=…"])`). Garde d'identité sous `node{ checkout scm }` ; puis `def b = build(job:, wait: true, propagate: false, parameters: [MANIFEST, ENVIRONMENT, ADMIN_VIA, MERGE_SHA, VAULT_USER, PasswordParameterValue(creds.V_PASS)])` **hors nœud** (parité du Groovy : aucun exécuteur tenu pendant l'apply aval — le lab n'en a que deux) ; puis **verdict** : `b.result != 'SUCCESS'` ⇒ `FAILURE` ; `!(APPLIED_MODE == 'pinned' && APPLIED_SHA == MERGE_SHA)` ⇒ **`SHA_NON_CONFIRME`**, `FAILURE` même si l'aval est vert (le mode `pinned` ferme le cas « HEAD == MERGE_SHA par coïncidence, sans paramètre ») ; rapport sous `withEnv(['V_PASS='])` + `node` ; `error()`. La confirmation vient de l'aval **qui a fait le checkout** ; `SHA_NON_CONFIRME` **détecte** (seconde ceinture : Jenkinsfile aval d'avant A2, checkout raté), `MERGE_SHA_REQUIS` **ferme**.

### D4 — Le digest du palier : `app_manifest_digest_env`

Quatrième fonction de `scripts/lib/app-manifest.sh` : `app_manifest_digest_env <fichier> <env>` imprime `sha256:<hex>` = SHA-256 du **JSON canonique du manifeste effectif du palier** — la racine (sans `per_env`) fusionnée avec `per_env[<env>]` selon la sémantique exacte du rôle (`resolve-env.yml` : `combine(recursive=True)`, mappings fusionnés récursivement, listes et scalaires remplacés) — relu par `yaml.BaseLoader`, `json.dumps(sort_keys=True, separators=(",",":"), ensure_ascii=False)`, UTF-8. Refus : `PALIER_INVALIDE`, `MANIFESTE_INVALIDE`/`MANIFESTE_LEGACY` (lecture existante), `PALIER_ABSENT` (paliers déclarés nommés).

- **Canonique et pas les octets** : le digest répond à « qu'est-ce qui tourne », pas « quels octets » (le SHA couvre les octets).
- **Manifeste effectif, pas le seul bloc** (amendé à la critique) : `enforce`, `description`, `audience`… ne sont pas comparés par le contrat A1 ; une édition manuelle de la racine change ce qui tourne — le digest la couvre. Un autre palier n'y entre pas.
- Sert trois fois : le rapport de PR (D5), la confrontation aval/amont (D3, via `APPLIED_DIGEST`) et la détection `PALIER_SUPPLANTE` (D2).

### D5 — La PR comme tableau de bord : SHA et digest, trois marqueurs

`scripts/provision-apply-comment.sh` : entrées optionnelles `APPLIED_SHA` (ligne « référence appliquée » + lien `<GIT_WEB_HOST>/<repo>/commit/<sha>`), `EXPECTED_SHA` (la référence **demandée**, écrite quand elle diffère), `APPLIED_DIGEST`, `REFUSAL`, `REFUSAL_DETAIL` ; `APPLY_RESULT=REFUSED` accepté sans `VALIDATOR`. **Assainissement au puits** : tag borné `[A-Z][A-Z0-9_]{2,40}`, SHA et digest ignorés s'ils n'ont pas la forme, détail sans saut de ligne ni syntaxe markdown active, tronqué, en code span. Trois marqueurs : `<!-- provision-apply -->` (résultat d'un apply réel : SUCCESS/FAILURE/ABORTED/`SHA_NON_CONFIRME`), `<!-- provision-apply-refus -->` (refus avant la pause), `<!-- provision-apply-build -->` (statut build, `post{always}`, **gaté par `GITEA_HEAD_REF`** relu — jamais par le `PR_BRANCH` du payload). Pour `SHA_NON_CONFIRME`, le corps dit la vérité : « l'aval a projeté X, PAS la référence demandée Y — état de la gateway à vérifier, repli A6 à envisager », jamais « PAS déployée ». Corps **identique à aujourd'hui** pour les appelants sans les variables neuves.

### D6 — `ADMIN_VIA` devient un point de configuration, pas une constante

`APPLY_ADMIN_VIA = "${env.APPLY_ADMIN_VIA ?: 'proxy-oauth2'}"` : le défaut est celui du XML d'avant (modèle client). Lab : `direct`, variable globale Jenkins (script console, même classe qu'`APIM_DIRECT_BASE_TPL`), documentée dans `ENVIRONNEMENTS.md`. Ce n'est **pas** A3.

### D7 — Ce qui ne change pas

Le rôle Ansible, `provision-request.sh`, `provision-plan`, `provisioning-request` (A0 restant), `env-chain.sh`, le credential (A3), l'axe déployeur (A4), la porte API (A5), le repli (A6), le terminus (A7). `assert-merge-identity.sh` n'est pas modifié : seules ses **entrées** changent de source.

### D10 — Limites, écrites d'avance

- En `rec`, l'apply atteint **la même 10.15** que `dev` (`X-Environment` ignoré par la voie directe) : l'état que le GOAL dénonce et qu'**A3** corrige ; A2 prouve la **référence**, pas le palier.
- **Le quatre-yeux du maillon 2 ne prouve pas « demandeur humain ≠ valideur »** : l'auteur de la PR est le compte de service `ci` par construction (`provision-request.sh:302`), le demandeur humain n'est que dans le corps de la PR. `GITEA_REQUESTER=ci` ne rend `FOUR_EYES_VIOLATION` atteignable que si le mergeur est `ci` lui-même (déjà refusé par `MERGER_MISMATCH`). Le contrôle réel est le merge par un humain autre que le demandeur — protection de branche Gitea (G4), hors A2 ; même limite que `team-promote.sh`.
- **La garde de périmètre vit dans le dépôt que la PR modifie** (PPE indirect, GOAL cd-promotion l.56) : elle reste contournable tant que `ci/stoa-labs@main` n'est pas protégée ; la fermeture est G4 (`setup-repo-protections.sh`, `protected_file_patterns` sur `ci/**;scripts/**;ansible/**`) — prérequis nommé de l'affirmation « la PR est le fichier de déploiement », pas une puce « hors périmètre ». Direction structurelle (OWASP) : sortir `clients/provisioned/**` du dépôt plateforme, repo-par-projet comme pour les APIs.
- Le secret HMAC du webhook n'est pas vérifié en aval (GWT 2.4.2) : la réconciliation **est** la garde.
- Un humain qui lance `selfservice-app-deploy` à la main avec un `MERGE_SHA` sur la lignée de `main` applique cet état-là — le levier d'A6, borné par l'identité nominative et Vault.
- `PALIER_SUPPLANTE` compare au `main` du moment de la réconciliation ; une PR mergée pendant la pause d'une autre (même palier) n'est pas vue par la pause déjà ouverte — `disableConcurrentBuilds` sérialise les builds, pas les décisions ; l'ordre des applies suit l'ordre des builds.
- **Dette tracée, hors A2** : `team-promote.sh` partage la classe corrigée ici (refus et ✅ sous un seul marqueur `<!-- team-promote -->`, commentaire sur le `PR_NUMBER` du payload, valeurs brutes dans `fail`) — à reprendre à part.
- La suite live crée un compte Gitea `alice` (collaboratrice `write`) : geste additif documenté, même nature que le compte `oscar` posé par le harnais d'onboarding.
