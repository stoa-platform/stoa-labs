# A5 — L'ordre app/API : refus fermé si l'API n'est pas au palier

## Porte (reprise du GOAL, non négociable — et ÉLARGIE par le spike)

- Avant tout geste sur la gateway, l'apply vérifie que `api@api_version` **existe et est active** dans la gateway du palier. Sinon refus nommé, **rien écrit**, message sur la PR nommant la promotion d'API manquante.
- **Spike S2 (2026-09-02, 10.15 réelle)** : la gateway refuse l'UUID inexistant (400, sans fantôme) mais **accepte** la souscription à une API inactive (200, relue, trafic 404, survit à l'activation) ; le moteur Python refuse l'absente (rc 1, échec de résolution sans tag) et accepte l'inactive (rc 0) ; il résout par `apiName` seul. **Une souscription posée puis retirée brûle la paire** (S1-T3, ré-inscription 500 irréversible) : la porte doit précéder le `PUT …/apis`, elle ne peut pas être « poser puis défaire ».
- **Élargie** (spike, conclusion 2) : `name + version + isActive`, trois refus nommés — `API_NOT_PROMOTED` (aucune version de ce nom au palier), `API_VERSION_MISMATCH` (le nom y est, pas cette version), `API_INACTIVE` (présente, inactive).
- **Porte A5 :** application en rec, API jamais promue en rec ⇒ `API_NOT_PROMOTED`, aucune application créée ; promouvoir l'API (G5) puis rejouer ⇒ application créée, **souscrite au GUID promu**.
- **Contre-épreuve :** API présente mais **inactive** en rec ⇒ refus (une souscription à une API inactive est une souscription à rien).

## Hypothèses (session autonome — ce qu'un humain aurait tranché)

1. **La porte vit dans le rôle Ansible**, pas dans un script extrait de `origin/main` (D0). Raison : c'est le seul site qui tient le credential du palier ; la garde A3 ne touche jamais la gateway et ne lit jamais le corps du ticket (invariant A3, `selfservice-palier-gate.sh` en-tête) ; « seul un playbook Ansible passe » chez ce client pour ce qui parle à la gateway. Conséquence assumée : la porte suit la lignée du rôle **épinglée au SHA appliqué** (D7, limite écrite).
2. **Trois tags, pas un** — ceux que le spike a nommés et que le GOAL a repris. `API_AMBIGUE` s'y ajoute (deux entrées même nom même version : la 10.15 ne devrait pas le produire ; fail-closed plutôt que `first`).
3. **`isActive` absent ⇒ inactif.** « Ne pas savoir n'est pas une raison de passer » (motif `teams-feature.yml`). La 10.15 réelle porte le champ dans la liste `GET /apis` (mesuré le 2026-09-03 : 13 APIs, 5 inactives, clés `apiName apiVersion id isActive …`) ; le mock aussi (`apiEnvelope`, `archive_test.go:278`). Un booléen JSON strict — jamais la chaîne `"true"`.
4. **Le moteur Python (prototype, spec du fold-in Go) reçoit la même porte** — le spike l'a mesuré sans porte et l'a écrit comme dette ; la laisser divergente du rôle serait un écart G8 à enregistrer. Cinq lignes, même tags, `exit 1` avant tout `POST`.
5. **Le plan (`provision-plan`) ne sait pas** : lecture seule, identité de job, aucun credential gateway. Le demandeur apprend le refus **à l'apply**, sur la PR, avec le remède nommé. Pas de sonde anonyme de la gateway depuis le plan (une gateway d'admin ne répond pas sans credential, et le plan ne doit en tenir aucun).
6. **Sur le lab mono-gateway, « promouvoir l'API vers rec »** n'est pas jouable tel quel (dev/rec/int = une seule 10.15 ; G5 tourne mock→mock vers `wm-mock-prod`) : la porte est prouvée par builds réels sur **les trois situations que la gateway du palier peut présenter** — nom absent, version absente, API inactive (désactivée puis réactivée, trap) — et le « rejeu après promotion » est le rejeu après **réactivation** du même objet, GUID identique relu.

## État courant (relevé du 2026-09-03, à ne pas re-dériver)

**L'apply d'application en CI = le rôle `ansible/roles/apim_selfservice_app`**, lancé par `ci/Jenkinsfile.selfservice` (stage Apply, `sh` sous `set -eu` + trap de révocation) : login nominatif → garde A3 (`selfservice-palier-gate.sh`, Vault seulement) → préflight de joignabilité (`/health`, sans credential) → `vault_token_ttl` → `ansible-playbook ansible/selfservice-app.yml -e apim_ss_manifest=… -e apim_ss_env=… -e apim_ss_team=… -e apim_ss_api_base=… -e apim_ss_vault_wm_creds_sub=…` → `ansible/selfservice-app-verify.yml` (mêmes `-e`) → annonce `APPLIED_*` (A2). Le moteur Python `scripts/apply-selfservice-application.py` n'est **pas** dans la chaîne (prototype, « spec vérifiée » du fold-in `labctl apply-consumer`).

**Ordre du rôle (`tasks/main.yml`), lectures puis PREMIÈRE écriture :** `resolve-env.yml` (manifeste effectif = racine ⊕ `per_env[env]`) → `apim_common/secrets.yml` (creds du palier, Vault ; fallback PoC `Administrator/manage` sans `VAULT_ADDR`) → §0a sonde Teams (`GET /configurations/extended`, `TEAMS_PROBE_FAILED`/`TEAMS_DISABLED`) → §0 `team-name.yml` (`TEAM_UNDEFINED`) → **§1 `GET /apis` puis résolution `apiName == api` ET `apiVersion == api_version` → `assert` « API … absente — la publier d'abord »** → §1b `api-visibility.yml` (`GET /apis/{id}`, `API_NOT_VISIBLE_TO_TEAM`) → **§2 `GET /applications` puis `POST /applications` = la première écriture** → `PUT …/apis {"apiIDs":[id]}` (remplace) → identifiers → IAM → routing → auth. Aucune tâche avant §2 n'écrit (vérifié : aucun `method:` dans `teams-feature.yml`, `team-name.yml`, `api-visibility.yml`). **Ce qui manque** : `isActive` n'est lu nulle part ; le refus « absente » est un `assert` anonyme (pas de `REFUS: <TAG>`, rien dans `REFUS_OUT`) ; le nom seul présent en une autre version rend le même « absente ». `verify.yml:165-175` résout de même (nom + version) puis **ne vérifie ni l'activité ni la souscription** (`consumingAPIs` n'y apparaît pas) — `ENFORCEMENT_CONFIRMED`/`OUTBOUND_CONFIRMED` sont structurels.

**Le relais d'un refus jusqu'à la PR (A4, fait Jenkins 11 mesuré) :** la garde A3 écrit le TAG dans `REFUS_OUT="$WORKSPACE/.a3-refus"` avant son `exit 1` ; `post { always }` du stage Apply relit le fichier sous la classe `[A-Z][A-Z0-9_]{2,40}` → `env.APPLIED_REFUSAL` → `buildVariables` → `ci/Jenkinsfile.provision-apply:332-340` : `env.REFUSAL = APPLIED_REFUSAL`, `env.REFUSAL_DETAIL = "refus de la garde du palier dans l'aval … — voir sa console (rien n'a été écrit sur la gateway)"` → `scripts/provision-apply-comment.sh` (`clean()` sur le détail, `REFUSAL_KIND=porte` ⇒ paragraphe de remède). **Un refus du rôle n'entre pas dans ce relais** : la PR dit « EN ÉCHEC — voir la console ». Le commentaire de `Jenkinsfile.selfservice:618-623` le dit : « Seuls les refus de la GARDE portent un tag ».

**La 10.15 réelle du lab, mesurée le 2026-09-03 :** `GET /rest/apigateway/apis` (Accept JSON) ⇒ `apiResponse[].api` avec `apiName`, `apiVersion`, `isActive` (booléen), `id`, … ; `demo-selfservice 1.0.0` active `658620e8-…` ; `accounts-read` en DEUX versions (`1.0.0` active, `1.0.1` inactive) ; `customer-referential 1.2.0`, `payments-initiation 0.3.0`, `wm-admin-self 1.0` inactives. Le mock (`mocks/webmethods/admin.go:74`, `apiEnvelope`) sert la même enveloppe, `PUT /apis/{id}/activate|deactivate` existent (`server.go:65-66`), le data-plane répond 503 sur une API inactive. `provision-request.sh` ne valide `REQ_API` que par sa classe de caractères (`:160-166`) — aucune relecture de `publish.yml` — donc une demande peut nommer une API qui n'existe nulle part (la voie machine ; le formulaire `app-request` propose la liste de `publish.yml`, ergonomie, pas autorité).

## Décisions

### D0 — Le site : le rôle, à la place de l'`assert` §1 — la dernière lecture avant la première écriture

La porte A5 remplace la tâche « API : fail-closed si non publiée » de `tasks/main.yml` §1, **à la même position** (après la sonde Teams et l'équipe, avant `api-visibility.yml` et avant `POST /applications`). Ce n'est pas l'ordre des lectures qui est la propriété — c'est **l'antériorité à la première écriture**, et elle se prouve au journal d'un stub (D5) : sur un refus, aucun `POST`/`PUT`/`DELETE` n'atteint la gateway. Le Jenkinsfile **route** (il passe deux chemins de fichiers de plus), le rôle **décide**.

Pourquoi pas la garde A3 (mémoire « A5 va dans la garde A3 avant le préflight ») : la garde ne touche jamais la gateway et ne lit jamais le corps du ticket — l'y mettre ferait lire le credential du palier par un shell, ce qu'A3 a précisément retiré. Pourquoi pas un script à part extrait de `origin/main` : même raison (le credential), et le rôle porte déjà ses gardes (`TEAM_UNDEFINED`, `API_NOT_VISIBLE_TO_TEAM`) sur le même modèle.

Conséquences héritées gratuitement : **A6** (le repli est un apply comme un autre : même rôle, même porte — « `API_NOT_PROMOTED` tient aussi en repli ») et **A7** (au terminus, `apim_ss_api_base` est la base du terminus : « une application dont l'API n'est qu'en homol ne peut pas atteindre prod »).

### D1 — Le prédicat, en quatre refus nommés, sur la liste déjà relue

Une seule lecture, celle qui existe (`GET {{ apim_ss_api_base }}/apis` → `ss_apis`). Quatre `set_fact` puis un aiguillage, dans cet ordre :

| Situation (sur `apiResponse[].api`) | Tag | Phrase (le détail relayé à la PR — nomme l'API, la version, le palier, la base, le remède) |
|---|---|---|
| aucune entrée `apiName == api` | `API_NOT_PROMOTED` | `l'API '<api>' n'est pas au palier '<env>' (aucune version publiée sur <base>) — promouvoir l'API vers <env> (chaîne des APIs : PR promote/<api>-<env>, G5) puis rejouer l'apply ; rien n'a été écrit` |
| nom présent, aucune entrée `apiVersion == api_version` | `API_VERSION_MISMATCH` | `l'API '<api>' est au palier '<env>' en version(s) <v1, v2>, pas en '<ver>' — promouvoir cette version vers <env> (G5) ou corriger la demande (api_version est figé : une autre version est une NOUVELLE application, A1) ; rien n'a été écrit` |
| plus d'une entrée nom+version | `API_AMBIGUE` | `<n> entrées '<api>' v<ver> sur <base> — résolution impossible sans choisir, refus fail-closed ; rien n'a été écrit` |
| l'entrée unique n'a pas `isActive` **booléen vrai** | `API_INACTIVE` | `l'API '<api>' v<ver> est au palier '<env>' mais INACTIVE (isActive=<valeur ou absent>, id=<uuid>) — une souscription à une API inactive est une souscription à rien (spike S2 : acceptée par la gateway, trafic 404) ; activer l'API au palier (geste producteur) puis rejouer l'apply ; rien n'a été écrit` |
| sinon | — | `API_AT_PALIER : '<api>' v<ver> active au palier '<env>' (id=<uuid>)` (debug — le marqueur des preuves) ; `ss_api_id` posé |

`isActive` : `(entry.isActive | default(omit))` comparé par `is sameas true` — un champ absent, `null`, `"true"` (chaîne) ou `1` sont **inactifs** (hypothèse 3). Le message d'`API_INACTIVE` imprime la valeur vue, pour qu'un mock infidèle se diagnostique en une ligne (A7).

Les phrases ne portent **aucune valeur non bornée** venant de la gateway sauf la liste des versions et l'id (classe de la gateway) ; `api`/`api_version` viennent du manifeste, bornés par la lib A1 (`^[A-Za-z0-9._-]+$`). Le détail est de toute façon nettoyé par `clean()` avant la PR.

### D2 — Le relais : une lib de refus dans `apim_common`, deux fichiers, la même chaîne jusqu'à la PR

**`ansible/roles/apim_common/tasks/refus.yml`** (nouveau, additif) — entrées `refus_tag` (classe `[A-Z][A-Z0-9_]{2,40}`, assertée) et `refus_msg` (une ligne) ; effets, dans cet ordre : (1) si `apim_ss_refus_out | default('')` non vide ⇒ `copy` `content: "{{ refus_tag }}\n"`, `mode: '0600'` ; (2) si `apim_ss_refus_detail_out | default('')` non vide ⇒ `copy` du message, une ligne (sauts de ligne remplacés par un espace, borné 300) ; (3) `fail` avec `msg: "REFUS: {{ refus_tag }} : {{ refus_msg }}"` — la ligne que les consoles et les suites lisent. Aucune écriture gateway. Le rôle `apim_selfservice_app` l'`include_tasks` sur le verdict de D1. (Les autres gardes du rôle — `TEAM_UNDEFINED`, `API_NOT_VISIBLE_TO_TEAM`, `TEAMS_*` — restent des `assert` : hors périmètre, nommé en D8.)

**`ci/Jenkinsfile.selfservice`** : (a) les deux lignes `ansible-playbook` (converge ET verify) reçoivent `-e apim_ss_refus_out="$WORKSPACE/.a3-refus" -e apim_ss_refus_detail_out="$WORKSPACE/.a3-refus-detail"` ; (b) la garde A3 reçoit `REFUS_DETAIL_OUT="$WORKSPACE/.a3-refus-detail"` sur sa ligne d'appel ; (c) les purges absolues de `.a3-refus` (stage Référence + avant la garde) purgent aussi `.a3-refus-detail` ; (d) `post { always }` relit `.a3-refus-detail` → `env.APPLIED_REFUSAL_DETAIL` sous la classe `[^\r\n]{1,300}` (sinon vide) — et **seulement** si `.a3-refus` a donné un tag (un détail sans tag n'est relayé à rien) ; (e) le commentaire « Seuls les refus de la GARDE portent un tag » est réécrit : garde **ou rôle** (`refus.yml`).

**`scripts/selfservice-palier-gate.sh`** (additif, 3 lignes) : `REFUS_DETAIL_OUT="${REFUS_DETAIL_OUT:-}"` lu AVANT `refus()`, purgé en tête avec `REFUS_OUT`, et `refus()` y écrit `$2` (la phrase) quand posé. Ainsi `DEPLOYER_GROUP_REQUIRED`, `PALIER_FERME`, … arrivent sur la PR **avec leur phrase** au lieu de « voir sa console » — le même relais, une fois.

**`ci/Jenkinsfile.provision-apply`** : `def ad = (vars.APPLIED_REFUSAL_DETAIL ?: '').toString()` ; `env.APPLIED_REFUSAL_DETAIL = (ad ==~ /[^\r\n]{1,300}/) ? ad : ''` ; dans la branche `APPLY_RESULT != SUCCESS && APPLIED_REFUSAL` : `env.REFUSAL_DETAIL = env.APPLIED_REFUSAL_DETAIL ? "aval ${env.APPLY_BUILD} : ${env.APPLIED_REFUSAL_DETAIL}" : <phrase actuelle>`.

**`scripts/provision-apply-comment.sh`** : quand `refusal ∈ {API_NOT_PROMOTED, API_VERSION_MISMATCH, API_INACTIVE, API_AMBIGUE}` (ensemble explicite, pas un préfixe), après la ligne « L'application n'est PAS déployée. Refus `…` : `…` », un paragraphe de remède : « **L'ordre app/API** (A5) : une application ne précède jamais son API au palier. Promouvoir l'API vers `<env>` par la chaîne des APIs (`api-promote-request` → PR `promote/<api>-<env>` → merge → `team-promote`), ou l'activer au palier, puis **rejouer ce webhook** : rien n'a été écrit sur la gateway, cette PR reste la référence — inutile de rouvrir une demande. » (`<env>` = `ENV_NAME` nettoyé ; `<api>` n'est pas connu du script — il est dans le détail.)

### D3 — Verify : le même prédicat, plus la souscription relue

`tasks/verify.yml`, après la résolution `v_api_id` (`:165-175`) : (1) `API_AT_PALIER_CONFIRMED` — l'entrée nom+version existe, unique, `isActive is sameas true` (sinon **`refus.yml`** avec `API_AT_PALIER_UNCONFIRMED : …` — relayé à la PR comme tout refus, D2) ; (2) `SUBSCRIPTION_CONFIRMED : '<app>' souscrite à '<api>' v<ver> (id=<uuid>)` — `v_api_id in (v_apps.json.applications | selectattr('name','equalto', app) | map(attribute='consumingAPIs') | first | default([]))` (la liste relue en tête de verify, comme `main.yml` §2 ; sinon `refus.yml` avec `SUBSCRIPTION_UNCONFIRMED : consumingAPIs=<liste>`). C'est ce qui rend « souscrite au GUID promu » **lisible**, et ce qu'A6 comparera (même GUID avant/après repli). Verify est rejouable : une API désactivée après l'apply rougit au rejeu (`API_AT_PALIER_UNCONFIRMED`), ce que l'apply seul ne verrait plus.

### D4 — Le prototype Python : la même porte, mêmes tags (spec du fold-in)

`scripts/apply-selfservice-application.py` : la résolution `next(… apiName == api_name …)` devient nom + version (`m.get("api_version")`, obligatoire : `sys.exit("REFUS: CABLAGE_INCOMPLET : api_version absent")`) + `isActive is True`, avec les quatre tags de D1 imprimés `REFUS: <TAG> : …` et `sys.exit(1)` **avant** `GET /applications` (donc avant tout `POST`). Le spike `scripts/spike-cd-applications.py` S2-T3 (lecture du code : « compare apiName SEUL ») est réaligné sur le nouvel attendu (le moteur refuse l'inactive : rc 1, `API_INACTIVE` sur stdout) — le spike reste rejouable et dit désormais l'état vrai. Les manifestes JSON du spike reçoivent `api_version`.

### D7 — Rollout sur le lab, et la lignée de la porte

`git push gitea HEAD:main` **avant** la suite live : la garde A3 est extraite de `origin/main`, mais **le rôle est celui de l'arbre pinné au `MERGE_SHA`** (A2 : le stage Référence checkoute l'arbre entier) — une PR `provision/*` mergée après le push porte donc le rôle A5 dans son commit de merge. Aucun job re-posé, aucun XML touché, aucune globale Jenkins.

**Limite écrite d'avance (la lignée)** : la porte suit le rôle, épinglé au SHA appliqué. Un **repli (A6) vers un SHA antérieur à la livraison d'A5** rejoue le rôle d'alors, sans porte — un artefact du lab (chez un client, le rôle est livré avec A5 dès le premier SHA). Ce que ce périmètre tient déjà : une PR `provision/*` ne peut pas modifier le rôle (`PR_HORS_PERIMETRE`, A2), `main` n'est poussé que par `ci` (protection de branche) — la lignée du rôle est celle de la plateforme, pas du demandeur. A6 devra le dire (et, s'il le veut, épingler un plancher de SHA pour le repli).

### D8 — Limites et dettes, écrites d'avance

- **Le plan ne sait pas** (hypothèse 5) : le refus arrive à l'apply, sur la PR. Une relecture anonyme de la gateway par le plan supposerait un credential que le plan ne doit pas tenir.
- **TOCTOU de quelques secondes** entre la porte et le `PUT …/apis` : une désactivation dans cette fenêtre est la course propre de la gateway ; la souscription survit à l'activation (spike), et verify le dit au rejeu.
- **Mono-gateway** : sur le lab, « au palier rec » = « sur la 10.15 unique » ; la topologie par palier est celle du client (A3 D9 déjà). Le mock du terminus (`wm-mock-prod`) sert `isActive` (booléen Go) — A7 le prouvera par build.
- **Les autres gardes du rôle** (`TEAM_UNDEFINED`, `API_NOT_VISIBLE_TO_TEAM`, `TEAMS_DISABLED`, `ENV_UNDEFINED`, cert/IP) restent des `assert` non relayés : `refus.yml` existe désormais, les y router est un geste par garde (hors A5).
- **Le refus de verify** (`API_AT_PALIER_UNCONFIRMED`, `SUBSCRIPTION_UNCONFIRMED`) n'est **pas** un « rien écrit » : la convergence a eu lieu ; il est relayé par le même fichier (la PR nomme le tag), le paragraphe A5 s'y applique (l'API a bougé entre l'apply et verify).
- `API_NOT_VISIBLE_TO_TEAM` reste **après** la porte A5 : l'ordre « l'API est-elle là ? » puis « l'équipe la voit-elle ? » est celui d'aujourd'hui, et la visibilité exige l'id.
- Le formulaire `app-request` propose les APIs de `publish.yml` (chaîne d'authoring) — pas celles du palier : la liste est de l'ergonomie, la porte A5 est l'autorité.
